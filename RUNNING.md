# Running a MapHub

How a MapHub is set up, run and kept, for its maintainers: the repositories, setting up a copy step by step, participants and portfolios, the runs and their configuration, running unattended, and the stages. [`CLAUDE.md`](CLAUDE.md) sets up the host computer and lists what an AI assistant running it must not miss; this file is the full account. [RESULTS.md](RESULTS.md) says what a MapHub produces, and [DEVELOPMENT.md](DEVELOPMENT.md) how the scoring works and why. The method does not depend on the field; the examples and dates here come from the prototype (this repository: astro-ph and cs.AI).

## Repositories

The main repository is public. Its main branch holds `scorer/` (the daily table script), `viewer/` (the web viewer), `config-log.json` and the GitHub workflow that publishes the viewer; its tables branch holds the same plus `tables/`, and is the one published. Code and documents are developed on main, which stays the code alone, for copies and code releases; the host computer works on the tables branch, merging main into it before each run ([Runs, Pulls and merges](#pulls-and-merges)), and its pushes publish the viewer and tables. A snapshot of the tables for a paper is a release of the tables branch.

The main repository ignores `.work/`, where runs save papers and scores for resuming, `.cache/` (the arXiv OAI-PMH records for rebuilding past listings, the logs of every `mh` run, and scoring trials kept by hand in `.cache/trials/`; [DEVELOPMENT.md, Past listings](DEVELOPMENT.md#past-listings)), `.env`, for local settings such as an API key for the `api` route, and, on main, `tables/` (the tables branch adds them with `git add -f`). The scorer needs Python with `anthropic` and `pyarrow`.

The portfolios sit in `maphub-portfolios/` inside it, in one of two ways ([Setting up a copy, step 3](#setting-up-a-copy), below):

```text
maphub-public/        public: code, configuration log and viewer (main); the
                      same with the daily tables (tables)
  maphub-portfolios/  private, shared with all participants, who have read
                      access
```

- **A repository of their own** (the default, and the prototype's): private, cloned inside the main one and left out by `.gitignore`, so participants can read the portfolios while everything else is public.
- **A folder of the main repository** (remove the `maphub-portfolios/` line from `.gitignore`): simpler, with one repository to keep, but the portfolios are then exactly as visible as the main repository, public if it is public, as GitHub Pages on a free plan requires.

The scorer handles both: it checks that the portfolios are committed and pushed (only that folder, in the second case) and names their commit in each table's provenance. `portfolios-template/` holds a minimal start for either: `participants.json` and one portfolio in the format.

## Setting up a copy

The README ([Run your own MapHub](README.md#run-your-own-maphub)) gives these steps in short; here they are in full.

1. **Make your copy.** To start with a clean history, use GitHub's "Use this template", leaving "Include all branches" unchecked (the prototype is a template repository; to make your copy one too, tick 'Template repository' in Settings > General), or a release's code: this repository's main branch holds the code alone, and the prototype's tables are on its tables branch ([Repositories](#repositories), above). A fork carries the prototype's history, and GitHub leaves a fork's workflows off until you enable them on its Actions tab. Then, in a clone of your copy, create the branch your tables will go on, `git switch -c tables` and `git push -u origin tables` (it starts as main, and the first run adds the tables), and note which version you started from ([DEVELOPMENT.md, Versions](DEVELOPMENT.md#versions)).
2. **Choose the listings** in `config-log.json`. Keep one entry and edit it:
   - `listings`: the listings as arXiv's RSS feeds name them, such as `["hep-ph", "hep-th"]`.
   - `categories`: the arXiv API categories that past listings are rebuilt from when OAI-PMH fails (the fallback), one query each. Leave it out when every listing is a single category; an archive split into subcategories, like astro-ph or cond-mat, needs each one listed (see the prototype's entry).
   - `effective`: on or before the day of your first run, even a test; entries take effect by the date a run starts ([Configuration log](#configuration-log-and-provenance), below).
   - `model`, `effort`, `prompt` and `threshold`: the Claude model and effort level, the prompt version (in `scorer/daily_table.py`: `v2`, two passes with a cacheable prefix, the prototype's since Oct 19, 2026; `v1`, the same wording in an older order; `v0`, one pass) and, for two passes, the outline score from which a paper is scored again against the full portfolio (10 in the prototype, measured on astro-ph and cs.AI: [DEVELOPMENT.md, Two-pass test](DEVELOPMENT.md#two-passes-and-usage); worth checking on your own listings, for example with `--test`). `fallbacks` applies only to the API route. Replace `note`.
3. **Set up the portfolios** as `maphub-portfolios/` inside your copy, starting from `portfolios-template/`: one folder per participant, named by a pseudonym and holding `portfolio.md` ([README, Writing a portfolio](README.md#writing-a-portfolio)), and `participants.json`:
   ```json
   {"participants": {
     "1234": {"kind": "individual", "status": "active", "hidden": false, "since": "2027-01-04"},
     "5678": {"kind": "group", "status": "no-legacy", "hidden": false, "since": "2027-01-04"}}}
   ```
   - **Where they live:** a private repository of their own or a folder of your copy ([Repositories](#repositories), above); choose the folder only if your participants agree to public portfolios.
   - `status`: `active` is scored on each new listing and on backfills of past listings; `no-legacy`, new listings only; `paused` or `left`, not scored. `hidden: true` hides the column in the viewer without stopping its scoring. `kind` (individual, group or collaboration) and `since` (the date of the entry's latest change) are for your records, as is a dated log of changes beside the file, if you keep one (the prototype keeps `CHANGELOG.md`).
   - Pseudonyms are letters, digits, `_` or `-`, up to 40 characters; the prototype uses random numbers. Keep who stands behind each one where only participants can read it.
   - Commit and push every portfolio change before a run: the scorer refuses portfolios with uncommitted or unpushed changes, and the daily routine pulls them first. Portfolios kept as a folder of your copy are changed on main, like the code, and reach the host's tables branch with its next merge.
   - How you keep the portfolios, and how participants propose changes, is up to you; what the prototype does ([Participants and portfolios](#participants-and-portfolios), below) is a suggestion from its experience.
4. **Make the page yours:**
   - `viewer/index.html`: the title and description (lines 6–7), the full name in the header, the About panel (credits, contact, the GitHub link) and the footer's contact link; please keep the footer's "Built with MapHub" link, which notes the origin;
   - `viewer/viewer.css`: the colors at the top (the prototype's are Michigan Blue and Maize); `viewer/viewer.js`: the heatmap's color ramps, near the top;
   - the icons `viewer/favicon.svg`, `favicon-32.png` and `apple-touch-icon.png`;
   - the README, and `CLAUDE.md`, the operations file for an AI assistant, written so that it serves any MapHub, with the prototype's values as examples; replace those with yours;
   - `MAPHUB_USER_AGENT` in `.env`: how your MapHub names itself to arXiv and DataCite, with a contact, such as `MapHub (+https://github.com/<you>/<repo>; you@example.edu)`;
   - optionally, in `.env`, `MAPHUB_TIMEZONE`, the time zone of every time the logs, the driver, and `mh --status` show (default `America/New_York`, written `ET`; any name such as `Europe/Berlin`), which changes only the display, since arXiv's schedule stays Eastern time. Also optional, `MAPHUB_LOG`: what the logs of `mh` runs keep, `brief` (the default), `full`, or `off` ([Running unattended](#running-unattended), step 6).
5. **Publish:** in your repository's Settings > Pages, set the source to GitHub Actions, and in Settings > Environments > github-pages, let the tables branch deploy (Deployment branches; if the environment is not listed yet, GitHub creates it with the first deploy, which it refuses until the branch is added); each push of tables then deploys the viewer at your Pages address.
6. **Run it** each morning after arXiv's 20:00 ET announcement, with `python scorer/local_run.py -l` ([Local runs](#local-runs), below), on the tables branch of one host computer (on main, the script stops and says so).

   It needs either Claude Code (`claude` on the search path, recent enough for `--json-schema`), signed in to a Claude subscription whose terms allow this use (check them), whose usage limits then pace the runs; or the Claude API, with `ANTHROPIC_API_KEY=...` in `.env` and `--via api`. For scale, see [Stages, Cost](#stages) (below). `CLAUDE.md` sets up the host computer, with a short `mh` command for these runs. Once the routine works, the driver can run it unattended ([Running unattended](#running-unattended), below).
7. **Optionally, go back in time:** `local_run.py -b` scores one earlier listing for participants with status `active`, and `-bb` keeps going until the usage limit stops it, or until the surveyed categories begin, where it stops by itself. For a long way back, first seed the cache from arXiv's metadata snapshot (Kaggle's "arXiv Dataset", about 1.9 GB): `python scorer/arxiv_snapshot.py convert <the ZIP> <folder>` converts it on any computer, and the folder, copied into `.cache/arxiv-snapshot/` on the host with the driver stopped, is merged by the next backfill, once; the docstring gives the other steps, and the same tool lists the papers earlier backfills missed, which `daily_table.py --late` scores ([DEVELOPMENT.md, Past listings](DEVELOPMENT.md#past-listings)).

## Participants and portfolios

Participants are individuals and groups or collaborations, each shown by a pseudonym. Each participant's portfolio is the only input that scores papers for them, in the format of the [README, Writing a portfolio](README.md#writing-a-portfolio). The relevance score doubles as a proxy for answering capability: the participants a paper is most relevant to are taken as the ones best able to answer questions about it. They are not necessarily the best, but relevance is the only measure available, and the proxy improves as participants revise their portfolios; how well the scores match participants' own judgments is tested by a blind rating study ([DEVELOPMENT.md, Measurements, Rating study](DEVELOPMENT.md#stability-and-quality)) and described in a research note published in Research Notes of the AAS (10, 329; [doi:10.3847/2515-5172/aebf5c](https://doi.org/10.3847/2515-5172/aebf5c); [ADS](https://ui.adsabs.harvard.edu/abs/2026RNAAS..10..329C); [arXiv:2611.07174](https://arxiv.org/abs/2611.07174)).

- **First portfolios.** [README, The portfolio-drafting prompt](README.md#the-portfolio-drafting-prompt). A group's or collaboration's draft may be discussed with them before or after it goes into use.
- **Outline.** The scorer cuts each portfolio's outline at run time and never stores it ([README, Writing a portfolio](README.md#writing-a-portfolio)).
- **Names and instructions.** There is no separate author bonus. Participants who want one add names of people they know, and they may add scoring instructions; both count toward the portfolio's length. Since each full-pass request scores one participant, they affect only that participant's column; they stay out of the outline, so the outline pass, which serves everyone at once, never sees them. Instructions that inflate someone's scores would also make them look like a better person to ask, so the maintainer's review of portfolio changes watches for them.

How a MapHub keeps its portfolios is up to its maintainer; the prototype's practices below are suggestions from its experience.

- **Safeguards.** Each participant has a folder in the portfolios repository holding their portfolio. In the prototype, participants have read access to that repository only: they cannot push, and propose a change by forking the repository and sending a pull request, which the maintainer reviews (own folder only, length) and merges; emailing a new version works too.
- **Privacy.** Every participant can read every portfolio, since GitHub grants read access per repository, not per folder or branch. A participant who needs theirs private uses the own-repo option ([DEVELOPMENT.md, Extension directions](DEVELOPMENT.md#extension-directions)). Portfolios and the papers' abstracts are also sent to Anthropic, the provider of the language model, with every scoring request, under the terms of the account used ([README, What participants agree to](README.md#what-participants-agree-to)).
- **Participant changes.** The portfolios hold `participants.json`, each participant's current status and whether their column is hidden ([Setting up a copy, step 3](#setting-up-a-copy)); the prototype also keeps `CHANGELOG.md`, a dated log of joins, status changes and renames, in step with it. A portfolio without an entry is skipped with a warning. Data files are never changed when someone pauses or leaves: their past columns stay in the public tables, which participants are told when they join. Instead, the scorer publishes the active and hidden lists in `tables/participants.json`, and the viewer leaves out hidden columns (also from the similarity sorting) and grays out visible columns of participants who are no longer active.

## Runs

### Local runs

Scoring needs the portfolios in `maphub-portfolios/` ([Setting up a copy, step 3](#setting-up-a-copy)). The maintainer runs MapHub from one host computer, set up as `CLAUDE.md` describes. The daily routine runs through Claude Code on whichever seat `claude` is signed in to (it must be installed and signed in), with the column of every participant scored daily (status active or no-legacy; backfills: active):

```bash
python scorer/local_run.py -l    # --latest, in the morning: score the current listing, push it with any waiting backfills
python scorer/local_run.py -b    # --back: fill a missed day, else one listing further back; commit locally
python scorer/local_run.py -bb   # --back-all: keep backfilling until the usage limit stops it
python scorer/local_run.py -p    # --push: push waiting backfills when there is no new listing
# add -y (--yes) to push without confirming the commit message
```

Pushing a table starts "Publish viewer", which deploys the viewer and tables on GitHub Pages. A deploy can fail on GitHub's side with no fault in the code (once in the prototype: on Nov 25, 2026, `deploy-pages` found no "github-pages" artifact that the step before had uploaded), and GitHub emails the repository's owner. To deploy again, start the workflow fresh: Actions > Publish viewer > Run workflow, branch `tables`, which deploys what the tables branch holds now. Re-running the failed run instead deploys its own commit, which would put older tables back if a later push has deployed since.

arXiv announces each listing at 20:00 ET, and a run any time after that scores it; `CLAUDE.md` names the commands above `mh`. A backfill takes first any gap, a weekday between the earliest and latest tables without a table, otherwise the weekday before the earliest table; `-bb` also spends the seat's weekly limit, so the maintainer chooses when to run it.

Every mode first finishes a day left unfinished in `.work/`, so a day stopped by the usage limit needs no manual step; a backfilled listing with nothing left to score gets an empty table, so that every weekday has one. In the prototype, backfills score every participant, all with status active, so the recent tables are complete.

### One commit a day

To keep one commit a day, a backfill is committed locally and waits: the next `--latest` (or `--push`, when there is no new listing) folds the waiting commits and the new table into one commit, whose message gives the provenance once for each group of tables that share code, portfolios, configuration and columns, under their dates and newest first, with the papers and full-pass counts summed and a line only one table has kept with its date; its subject names the dates as ranges of consecutive weekdays (`Tables for Oct 15, Sep 1–7, 2026`). Commits go in the order things happened. A table commit made away from the host (papers the backfills missed, added with `daily_table.py --late`, or columns rescored with `--rescore`) takes the same form, says where it was scored, and is pushed only while the host's driver is stopped or asleep.

### Pulls and merges

If a table was pushed meanwhile from another computer, the pull rebuilds `index.json` (and the top-paper summaries) from the tables present. On the tables branch, each run then merges any new commits of main into the branch as last pushed, pushes the merge ("Merge main into tables: code pickup"), and replays the waiting backfills on top of it; main never touches `tables/`, and the tables branch changes nothing else, so the merge has no conflicts. Each table's provenance names the code that scored it (`Code: maphub-public <commit>`, the last commit that changed `scorer/`), so a waiting backfill replayed on top of newly pulled code still says which code it used.

### Configuration log and provenance

**Configuration log.** `config-log.json` records each change with the date it takes effect: model, effort, prompt version, input (abstract only or full text), listing (new submissions only or extended), the arXiv listings followed (`listings`, as named in arXiv's RSS feeds, such as astro-ph or cs.AI) and the categories past listings query in the arXiv API (`categories`: an archive split into subcategories, like astro-ph, needs each subcategory listed), chunk size, the two-pass threshold and similar settings. Entries apply by the date a run starts (Eastern time), not the listing it covers: an entry dated the next day leaves that evening's runs on the old configuration, so date an entry for the day it is committed unless a later start is meant. Changes should be rare. The prototype's first entry (Oct 5, 2026) is Claude Opus 5.5 at low effort with prompt v0. Trial runs of other models (`--model` and `--effort`, allowed only with `--test`) leave the log unchanged and write to their own folders.

**Provenance.** The tables carry no provenance themselves: each commit that adds or changes a table names, in its message, the portfolios commit, the configuration entry, the columns scored and the papers left out as already scored, so `git log -- <table>` gives the table's history even when a file holds columns from several runs or is corrected later. The scorer writes this message to `.work/commit-message.txt`, and `local_run.py` commits with it. A rescored table replaces the old one, and git keeps the earlier version.

### Running the scorer directly

The scorer can also be run directly, for example for a test; through Claude Code it scores only the columns named in `MAPHUB_OWN_PARTICIPANTS` (comma-separated pseudonyms; `local_run.py` sets it to every participant scored):

```bash
pip install -r scorer/requirements.txt
MAPHUB_OWN_PARTICIPANTS=<pseudonym> python scorer/daily_table.py --test   # 5 papers of each listing
python viewer/serve.py                   # viewer at http://localhost:8000/ (on main, add --tables <a checkout of the tables branch>/tables)
```

**Kinds of run.** Without a date, the scorer takes the current listing and stops at once if it is already in the tables, so repeated runs after a late announcement cost nothing. A past date is the legacy survey ([RESULTS.md, Back catalogs](RESULTS.md#back-catalogs)), scoring participants with status active; `daily_table.py DATE --daily` scores it as a daily run instead (no-legacy included), which `local_run.py` uses to finish a morning listing interrupted by the usage limit. `daily_table.py DATE --meta-only` checks an existing table against DataCite and writes its metadata fallback, without scoring; `--meta-only` also takes a list of dates (`2005-09-27,2005-09-28`), a range (`1992-04-15..2007-04-02`, every listing with a table in it), or a file of dates (`@dates.txt`), and commits what it writes as a commit of its own, with the driver stopped ([Running unattended](#running-unattended), step 6). `--test` scores 5 papers of each listing into the work dir.

## Running unattended

The driver (`mh -d`, `scorer/driver.py`) runs the routine above on the host computer: `mh -l` each weekday morning, `mh -bb` the rest of the time. Once the legacy survey is complete, only the morning runs are left (and any gaps to fill). Its times are constants at the top of `scorer/driver.py`, yours to choose (`SESSION` follows Claude Code's limits): the morning run from 02:00 ET (`MORNING`), so that the listing is in the viewer by about 07:00 even after a usage-limit wait; no time for review (`REVIEW`, 0 in the prototype; a MapHub may give its maintainer an hour, say); a retry every 30 minutes after a failure (`RETRY`), except where waiting cannot help (step 6); after a 5-hour limit, a wake at the reset; and no other sleep longer than 2½ hours (`WAKE`), such as during a weekly limit (each try then stops at once) or when Claude Code gives no reset time.

1. **Start it** in the main repository's folder, on the tables branch, in the background:
   ```bash
   nohup mh -d >/dev/null 2>&1 &
   mh --status
   ```
   `mh --status` shows the driver (running since when, what it is doing, and until when, or since when it has stopped, that it ended without stopping, or that it crashed), the tables (the first and last listing, how many, and the last push), the usage limit (in force, or the last one and when it ended), the last problem (a warning, an error, or a wait for you, with its time and when it cleared), then the commits waiting to be pushed, any listings set aside, and warnings still standing (step 6). It reads the driver's state in `.cache/driver/`, so it works with any `MAPHUB_LOG`. Only one driver runs at a time; a second `mh -d` says so and exits. Under WSL, keep the distribution running (a terminal left open, for one): when WSL shuts it down, the driver stops with it.
2. **Each morning.** From 02:00 ET the driver runs `mh -l` until the day's listing has a table, then pushes it with any backfills waiting, and "Publish viewer" updates the page. With a time for review (`REVIEW` above 0), the driver waits that long before pushing: to look at the commits first, run `mh -p` in a terminal, which shows the commit message (one group of dates per provenance: [One commit a day](#one-commit-a-day), above) and asks, `y` pushing now; to keep them waiting, run `mh --hold`, then `mh -p` whenever ready; backfills pause meanwhile. On Saturdays and Sundays (Eastern time) the driver pushes nothing: backfills, and a listing finished late, wait as local commits, and new code from main is merged on Monday morning's run; `mh -p` run by hand still pushes.
3. **Usage limits.** The driver keeps four rules (written out at the top of the usage-limit code in `scorer/driver.py`). A limit is weekly when Claude Code's message says "weekly" or its reset is more than 5 hours away; any other is the 5-hour limit. The driver sleeps until a few minutes after the reset (during a weekly limit, it checks again every 2½ hours, quietly), and if a run still meets the same limit after its reset, it tries again every 30 minutes. Each limit is said once, for its reset time. A weekly limit ends only when a request scores again, or when a run after its reset meets no limit (a run that only commits an empty table or pushes does not end it); "Weekly limit over" then says so. While a limit lasts nothing is scored, not even the morning listing; the day's saved requests stay in `.work/`, and the next run finishes the day. To use another seat meanwhile: `mh --stop`, sign in to the other seat, `mh -d`. Once a weekly limit resets, the first backfill fills the listings missed meanwhile, rebuilt by submission time like any past listing ([DEVELOPMENT.md, Past listings](DEVELOPMENT.md#past-listings)).
4. **Stop and restart.** `mh --stop` stops the driver once it finishes the listing it is scoring, or at once if it is sleeping or waiting for review (commits it has not pushed wait for `mh -p`, and a day left in `.work/` is finished by the next run); `mh --status` then says "not running". With no driver running, `mh --stop` says so and leaves no flag behind, so a later run is not stopped by it. A driver killed or shut down partway (a reboot, WSL closing) loses nothing either: start it again, and the first run finishes the day left in `.work/`. `mh --status` says that it ended without stopping, and the next start says so once in the log and keeps it as the last problem.
5. **Updating code, portfolios or the configuration.** Push to main from another computer: every run pulls and merges main first, so pushes reach the host on their own, at the latest when the next run starts (after a usage-limit sleep, a few hours; on weekends, at Monday morning's run, step 2); when the scorer's code (`scorer/`) has changed, the run that pulled it restarts with the new code before it scores anything, and the driver restarts itself between runs, so no listing is cut short. To edit on the host itself, stop the driver, wait until `mh --status` says it is not running, edit and commit, then start it again.
6. **When something goes wrong,** run `mh --status`, then read the log, `.cache/logs/mh-<date>.log` (one file a day, dated in Eastern time whatever `MAPHUB_TIMEZONE` says, all kept; before Oct 31, 2026, `.cache/driver/driver-<date>.log`). Every run of `mh` writes to it, the driver's and those started by hand in a terminal (marked `(by hand)`), as `MAPHUB_LOG` in `.env` says:
   - `brief` (the default): one line per event that matters, each with its time (`[Thu Nov 19 02:53 ET] Morning run`), and under it a line per listing scored, with its papers and usage; a backfill gives a line for each of its first five listings, then one line for every 10. A day of morning runs and backfills should take a few KB (an estimate, not yet measured). The commit messages are in git, not in the log.
   - `full`: every step, as the terminal shows it: each run as `$ mh …` with its output and its exit code in words (`exit 2 (stopped partway)`, `exit -15 (ended by a signal, SIGTERM)`), each request with its tokens, and the driver's lines. During the legacy survey a busy day wrote about 200 KB.
   - `off`: no log files; `mh --status` still shows the state and the last problem.

   The times are in `MAPHUB_TIMEZONE` (step 4 of [Setting up a copy](#setting-up-a-copy)). What the lines mean:
   - "Usage limit reached in <date> (its scores so far are saved); scoring resumes at …": normal; it tries again a few minutes after the reset (step 3).
   - "Weekly limit reached in <date> … No scoring until …": nothing is scored until the reset, the morning listings included, unless you switch seats (`mh --stop`, sign in to another seat, `mh -d`); the driver checks quietly every 2½ hours. The line "Weekly limit over" comes before the first request that scores again, or at the end of the first run after the reset time that meets no limit (step 3).
   - "… not finished, exit 1 (an error); trying again at …": a run failed for another reason (arXiv busy, a network error, a git conflict); it retries every 30 minutes. The line above it gives the cause, in the brief log as in the full one; in the full log, "GET failed … server is busy" lines are arXiv's rate limit, which the morning run outlasts by taking its metadata from the RSS feed. A request a server refuses as such (an error reply in the 400s other than 429, "too many requests") is not retried, since asking again cannot help.
   - "Error: stopped, 6 requests failed in a row …" and then "Backfilling stopped with no reset time given; trying again at …" (or, in the morning, "The morning listing not finished, exit 2 (stopped partway); trying again at …"): Claude Code failed without reporting a usage limit (an outage, say); the saved requests stay, and the driver tries again, within 2½ hours for a backfill and 30 minutes for the morning listing.
   - "Set aside <date>: it failed 3 runs in a row": a backfill listing that keeps failing no longer holds up the rest; the backfill goes on without it, `mh --status` lists it with its last error, and it is tried again after 7 days (`FAILS` and `RETRY_SET_ASIDE` in `scorer/local_run.py`), as often as needed. The morning listing is never set aside.
   - "Waiting for you: tables/ has uncommitted changes (…)": they may be your own work, so the driver never discards them; it says so once and waits, resuming by itself once they are committed or discarded. Unless they are your own, they most likely come from a run cut off between writing a table and committing it (a reboot, say): `git checkout -- tables` discards them, and the next run finishes the day from `.work/`. `mh --status` gives the same advice under "Last problem."
   - "Legacy survey complete; waiting for the next morning listing, …": said once a day; until the next morning listing the driver only sleeps (and, on a weekday, tries a failed push again every 30 minutes).
   - "Warning: pulling maphub-portfolios failed: …": the runs go on with the local copy of the portfolios, whose commit each table's message records; the warning is given once, and `mh --status` repeats it until a pull works. If git cannot reach the GitHub sign-in (when the driver was started from VS Code's terminal and VS Code has closed, say), restart the driver from a terminal where git signs in.
   - "Driver crashed: …" (the traceback follows it): a fault in the driver itself. It stops, and a run it had started is ended; `mh --status` shows "Driver: not running; it crashed: …" and keeps it as the last problem. Read the traceback and start the driver again (step 1) once the cause is fixed.
   - "The previous driver (pid …) ended without stopping": the driver was cut off (a reboot, WSL closing, a kill) rather than stopped; nothing is lost (step 4).
   - "Warning: DataCite could not be searched for <date> (HTTP …); the viewer looks these papers up one by one": only the metadata fallback for papers DataCite lacks is missing, which is rare (RESULTS.md); the table is complete. A search DataCite refuses is first split into smaller ones, down to one paper at a time, so this line means that DataCite itself failed. To write the fallback later, for a date, a list, or a range of dates, stop the driver first (`mh --stop`, then `mh --status` until it says not running; `--meta-only` refuses while the driver runs), run `python scorer/daily_table.py --meta-only <date>` (or `2005-09-27,2005-09-28`, or `1992-04-15..2007-04-02`, or `@<file of dates>`), which commits what it writes as a commit of its own ("Metadata fallbacks for …"), then push it with `mh -p` and start the driver again (step 1). Left uncommitted, the files would ride in the next table's commit.
   - "The push failed; the commits wait, and the driver tries again every 30 minutes between backfills" (after the push's error line): the commits wait as they were, unfolded, and the backfills go on. A backfill under way stops after its current listing when a try is due; the tries log nothing more until one works ("The push works again") or the error changes; `mh --status` shows the error as the last problem and counts the commits. If it lasts (a lost GitHub sign-in, say), fix the cause, or push by hand with `mh -p`.
   - "arXiv has not announced today's listing yet; checking every 30 minutes": said once a morning, when arXiv announces late or not at all (a holiday the driver does not know of yet).
   - "OAI-PMH failed (…); it rests until …": a backfill rebuilds its listing through the arXiv API instead; the harvested pieces stay in the cache, and OAI-PMH rests for two hours, then carries on from where it stopped. A run that starts during the rest says it once ("OAI-PMH rests until … after a failure at …").
   - "Warning: the OAI-PMH cache of <listing> for <month>: 1 of 1805 entries missing": the cache lacks a few of the papers arXiv announced that month (the check compares the month's IDs with arXiv's monthly listing page), so a listing rebuilt from it may lack them. A few missing entries need no action at once: `arxiv_snapshot.py missing` lists the papers of past listings that no table holds, from arXiv's metadata snapshot, and `daily_table.py --late` adds them ([Setting up a copy](#setting-up-a-copy), step 7). Many missing entries, or a warning that comes back for every month, point to a broken harvest; look at the cache's `state.json` before going on.

## Stages

The prototype's stages; a new MapHub goes through the same ones.

1. **Build and tune.** Several months of tuning the method and recruiting participants. Started Oct 2026, with the script, the viewer and the first five portfolios; Opus 5.5 at low effort was chosen after the full-day check. Two-pass scoring (prompt v1) replaced one pass from Oct 15, after the two-pass test.
2. **Daily operation.** Each listing is scored every morning on a Claude Code seat, by the maintainer or by the driver ([Runs](#runs)), and the viewer updates on its own. Started with the Oct 6, 2026 listing, scored through the API; on a Claude Code seat since Oct 7; tuning goes on alongside.
3. **Legacy survey.** The MapHub goes back through earlier listings, from the present backwards to the first listing of the categories it surveys, where it ends by itself, building the back catalogs ([RESULTS.md, Back catalogs](RESULTS.md#back-catalogs)).
4. **Running the survey again (optional).** The back catalogs keep the scores of the portfolios they were scored with. If the participants find that their portfolios have changed enough, they may consider running the survey again, at a cost in seat usage on the scale of the survey itself. A range of tables can be rescored in one run, for the columns served, the others kept (`daily_table.py --rescore`; `arxiv_snapshot.py`'s docstring); the prototype did so for all five columns of its tables of Sep 8 to Oct 14, 2026, scored before the portfolios were put in their standard format ([DEVELOPMENT.md, Two passes and usage](DEVELOPMENT.md#two-passes-and-usage), Prompt or portfolios).

**Cost.** Through Claude Code, each column runs on the signed-in seat, so the seat's usage limits pace the backfills (the prototype runs on a Standard seat of a Claude Team plan, which includes Claude Code, with 1.25 times the Pro plan's usage per session and a weekly limit, as of October 2026; an ordinary day of about 200 papers for five participants takes about 1% of its weekly limit with prompt v2: [DEVELOPMENT.md, Two passes and usage](DEVELOPMENT.md#two-passes-and-usage) has the measurements); through the API, see [DEVELOPMENT.md, Budget](DEVELOPMENT.md#two-passes-and-usage). Subscription limits change over time, so test your own seat on a few listings before relying on these figures.

An estimate for the API route (Oct 2026): on Sonnet 5.5 (half Opus 5.5's price, but weaker at the top of the scale and on cross-topic matches; the prototype uses Opus 5.5 through Claude Code: [DEVELOPMENT.md, Choosing the model](DEVELOPMENT.md#choosing-the-model)), one year of astro-ph listings (20,648 new submissions in the listings from Oct 7, 2025 to Oct 6, 2026; other listings scale with their size) would cost roughly $37 for the first column and $10 for each further one with prompt v0, since they share the cached papers; the two passes of prompt v1 cut this to about a third ([DEVELOPMENT.md, Two-pass test](DEVELOPMENT.md#two-passes-and-usage)), and chunks of 100 might cut more.

**Continuity.** A MapHub depends on its maintainer and one subscription. If the daily runs stop, the published tables and the viewer remain, and anyone can resume scoring from a copy ([README, Run your own MapHub](README.md#run-your-own-maphub)).
