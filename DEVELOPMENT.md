# Developing MapHub

How MapHub works and why it works that way, with the tests behind its choices, where it could go, the parameters still to tune and its versions, for anyone who develops MapHub or builds one for other arXiv listings. [RUNNING.md](RUNNING.md) says how a MapHub is set up and run, and [RESULTS.md](RESULTS.md) what it produces; the [README](README.md) introduces MapHub and gives the portfolio format and the scoring rubric. The method does not depend on the field; the measurements and dates here come from the prototype (this repository: astro-ph and cs.AI; five participants when they were made), and their numbers carry over as orders of magnitude, scaled by the size of the listings and the number of participants. Dates record when something was measured or decided.

## Overview

- **One heatmap per announcement day.** Weekends have no listing, so they have no heatmap; an arXiv holiday has no announcement ([RESULTS.md, Holidays](RESULTS.md#back-catalogs)).
- **Rows:** that day's new submissions to the configured listings, without cross-lists and replacements ([Extension directions](#extension-directions)).
- **Columns:** participants, both individuals and groups.
- **Cells:** each paper's relevance to each participant, scored from that participant's portfolio on a 0–100 scale ([README, Scoring rubric](README.md#scoring-rubric)).

New listings are scored each morning through Claude Code, by the maintainer or unattended by the driver ([RUNNING.md, Running unattended](RUNNING.md#running-unattended)), and backfills go back a day at a time. The maintainer also handles the human side by hand: reviewing portfolio changes, helping new participants, answering questions. Publishing the viewer runs on its own.

**Listings.** The prototype follows astro-ph and cs.AI because AI papers interest some participants; cs.AI adds about two papers a listing scoring 30 or more, mostly for the participants who follow AI, and the other participants can find AI papers of shared interest there; it adds few high scores to the other columns, though their outline pass still reads it. The prototype's legacy survey scores the same listings for every column, as its daily runs do. The listings are a setting in the configuration log (`listings` and `categories`), so a MapHub for other fields changes them there; the rest of what is the prototype's own (the page's wording and colors, the user agent, the operations file's examples) is listed in [RUNNING.md, Setting up a copy, step 4](RUNNING.md#setting-up-a-copy).

## Daily table

The script `scorer/daily_table.py` takes an announcement date (by default the current listing) and produces that day's table.

1. **Fetch.** The arXiv API cannot be queried by announcement date, so the day's new submissions come from arXiv's RSS feed for the configured listings (astro-ph and cs.AI in the prototype), which shows only the current listing and marks each paper's announce type (keeping "new" leaves out cross-lists and replacements). Titles, authors and abstracts then come from the API in one query, or from the feed itself when the API refuses (it carries the same fields: the same 257 papers for Oct 16, 2026, either way); nothing more is used. A past listing is rebuilt instead, by submission time, from a local cache of arXiv's OAI-PMH records, with the API as the fallback ([Past listings](#past-listings)). The papers are saved locally, so a rerun on a later day still has them.
2. **Score.** Two passes (prompt v1 from Oct 15, 2026, and v2, the same wording in a cacheable order, from Oct 19; [Two-pass test, Caching test](#two-passes-and-usage)). The outline pass sends one Claude request per chunk of about 50 papers: the outline prompt ([Prompts](#prompts)), the chunk's papers, and every participant's outline (the joint outline), and gets back a score for each paper and participant. The full pass then takes, for each participant, the papers whose outline score is 10 or more (the `threshold` in the configuration log) and scores them again with the scoring prompt and that participant's full portfolio, in chunks of about 50; the other cells keep their outline scores.

   Under prompt v0 (in the prototype until Oct 14, 2026), every paper went through the full pass: one request per participant per chunk, which repeats the short abstracts rather than the long portfolios, roughly 7× fewer input tokens than one request per paper. On the API route, the papers block is then identical across participants, so it is cached; with a single participant the script skips caching, since writing the cache costs 25% extra and pays off only when others read it. Requests through Claude Code, the default, barely share that cache (Oct 2, 2026: 791k tokens written, 78k read); the outline pass sidesteps this by sending each chunk's papers once for everyone.
3. **Write.** The scores become one Parquet file per arXiv ID month ([RESULTS.md, Table format](RESULTS.md#table-format)), and `tables/index.json` gains the date so the viewer can find it; once a year is complete (it is over, and every weekday in it has a table), its top-paper summaries are written for the viewer ([RESULTS.md, Web viewer](RESULTS.md#web-viewer)). The scorer then asks DataCite whether it has every paper's DOI, and saves the metadata of any it lacks beside the table ([RESULTS.md, Web viewer](RESULTS.md#web-viewer)). Papers already in another date's table are left out first, so each paper is scored once and only once; a run that writes tables also requires the portfolios to be committed and pushed.
4. **Resume.** If a run is interrupted, it continues where it stopped: each request's scores are saved as they arrive (the outline chunks, then each participant's full-pass chunks), a rerun skips what is saved, and the Parquet files are written only once the table is complete. A run stops at once when Claude Code reports a usage limit, and after six failed requests in a row otherwise (a chunk that fails three times is left for the next run, and the scorer goes on to the next one). A reply that skips a few papers keeps the scores it has, and the retry asks only for the skipped ones (Sep 29, 2026: one chunk lost a paper three times running and stopped the run, before this fix).

**Two ways to send requests** (`--via`). `claude-code`, the default, uses Claude Code's print mode (`claude -p`) on the seat `claude` is signed in to, with tools and settings off and any API key withheld; it scores only the columns listed in `MAPHUB_OWN_PARTICIPANTS`, which `local_run.py` sets to every participant scored daily (status active or no-legacy); on a past date the scorer then keeps those with status active.

`api` uses the Claude API with a key from the environment (`.env`); the prototype has kept no key since Oct 10, 2026, and the route can return when needed. On the API route the script sends requests one at a time, in chunk-major order, so that under prompt v0 every participant reads the cache the first one wrote (20 requests, five participants and four chunks, took about 2 minutes on Oct 5, 2026); the Message Batches API costs half price, but caching inside a batch is best-effort, so one-at-a-time requests with cache hits cost less. `--batch` keeps that option for tests, with prompt v0 only.

A scheduled GitHub workflow scored the prototype's listings through the API from Oct 6 to Oct 8, 2026; it was retired because its runs could start hours late (6 h 40 min on Oct 7) or not at all, and because a Claude Code seat made the API unnecessary.

Writing a column into an existing table keeps the other participants' columns, and a run whose paper list differs from the table's is refused.

How runs are started and recorded (kinds of run, local runs, the configuration log) is in [RUNNING.md, Runs](RUNNING.md#runs).

## Past listings

How a past listing ([RESULTS.md, Back catalogs](RESULTS.md#back-catalogs)) is rebuilt from arXiv's records, and checked.

**The cache.** The papers come from a local cache of arXiv's OAI-PMH records (`.cache/oai/`, outside git), harvested by set (`physics:astro-ph`, `cs:cs:AI`) with each paper's first submission time, primary category, title, authors and abstract. OAI-PMH selects records by the date they last changed, so a harvest from a given day to today holds every paper submitted since that day; the cache keeps one such span per set, without gaps (a paper submitted in a window may have changed at any time since, so the span reaches from before the window to the present, over days already in the tables), extends it backwards in steps of at least 30 days, and tops it up from its last harvest. It grows in pieces of 10 days, each saved once complete, so a failed harvest loses only the piece it was on, and the next run carries on from there. A listing counts as covered once harvested three days after its window ends. Once the cache covers a month whole (six months back, since papers held for moderation keep their earlier submission dates), the backfill compares the month's entries in the cache with the total on arXiv's monthly listing page, one request per month and at most two months per backfill, and warns if they differ; every paper is still scored exactly once, since the windows tile time and a paper already in a table is never scored again. The arXiv API, one query per configured category (`categories` in the configuration log) and listing, is the fallback when OAI-PMH fails; how the two compare, in requests and in the papers found, is in [OAI-PMH test](#the-oai-pmh-cache).

**The snapshot.** Cornell publishes the metadata of every arXiv paper as one file, updated regularly (a download on Oct 30, 2026 held changes to Oct 23): the "arXiv Dataset" on Kaggle (`Cornell-University/arxiv`; its terms are on its page), with each paper's categories (the primary first), title, authors, abstract and the submission time of every version, as OAI-PMH's `arXivRaw` format gives them. `scorer/arxiv_snapshot.py` turns it into the cache's own monthly files for the sets of the configured listings (`convert`), rebuilds every listing that has a table from them and compares the papers (`check`), and adds them to the cache on the host (`merge`), where the cache's own harvests win for months it already holds; the cache then covers everything up to the snapshot's latest change, and OAI-PMH only tops up the weeks since. For the legacy survey this replaces harvesting back to 1992 (about 34 years of records, at one request per 1,000) with one download.

**Snapshot check (Oct 30, 2026).** The snapshot of Oct 23 (3.2 million entries) gave 395,537 papers in the astro-ph set from April 1992 and 208,821 in the cs.AI set from August 1993 (cross-lists included, as in a harvest; 394,860 with astro-ph or cs.AI as their primary category, the papers MapHub scores), about 0.9 GB of cache files. Rebuilt from it, the backfilled listings (Sep 2022 to Oct 2026, 1,050 listings) matched their tables but for 52 papers more in the snapshot, and none fewer. 13 of them, held for moderation, were in the tables of the days they were announced. The other 39 were in no table: papers revised after the cache's latest harvest carry the revision's date, so the pieces harvested backwards missed them, since the cache was topped up forwards only for recent listings (7 of 8 checked were revised or updated Oct 19–22, 2026). Since Oct 30, 2026 the cache is topped up to the present whenever it is behind, and the 39 were scored in one run (`daily_table.py --late`) and added to their listings' tables. The listings from the morning runs, taken from the RSS feed rather than rebuilt by submission time, differ as expected.

**Retries.** When the arXiv API is busy (429 Too Many Requests or 503 Service Unavailable, as on Oct 8 and Oct 16, 2026), the scorer waits 30 s, 60 s and then 2 min between tries, or as long as the reply's Retry-After asks, up to five tries; other failures get three quick tries. OAI-PMH, which has the API as its fallback, gets one 30 s wait on a busy reply and two tries otherwise, with 3 minutes for each page, since it builds up to 1,000 records before sending any (on the host, pages timed out at the earlier 60 s, Oct 30, 2026); after a failure, past listings come from the API for two hours before OAI-PMH is tried again.

**Checks against arXiv.** Against arXiv's own lists, 341 of 345 papers matched on Oct 6, 2026, 256 of 261 on Sep 15 and 304 of 326 on Aug 4; every difference was a paper held for moderation, which a rebuilt listing dates by submission rather than announcement. Since the windows tile time, every paper is scored at least once, at worst on a neighboring date; and since a run leaves out papers already in another date's table, at most once. A held paper claimed by both a rebuilt and an RSS listing stays with whichever table was written first (two such papers, 2610.03840 and 2610.03850, were in both the Oct 5 and Oct 6 tables and were removed from Oct 5, a one-time correction).

## Prompts

Two prompts, adapted from the reading prompts of Kaili Cao's own literature workflow and written for any subject, person or group. Both give the scale of the README's Scoring rubric and ask for JSON only, with no explanations. Since prompt v2 (from Oct 19, 2026), the instructions and the portfolio (or the joint outline) are the system prompt and the papers the message, so that a run's requests share a cacheable prefix; under v0 and v1, the instructions and papers came first and the portfolio or outlines followed, which shared a prefix only across participants of the same chunk ([Measurements, Caching test](#two-passes-and-usage)).

- **Scoring prompt** (the full pass, and every request under prompt v0): one participant's full portfolio. The portfolio may name people the subject knows and give scoring instructions, which the prompt follows only for that subject's scores.
- **Outline prompt** (the outline pass, prompts v1 and v2): every participant's outline, each labeled with their pseudonym, with a score for each paper and pseudonym; the model is told to judge each subject only by their own outline.

The exact wording is `PROMPTS` in [`scorer/daily_table.py`](scorer/daily_table.py), kept by version so that earlier tables can be traced.

## Measurements

The tests behind MapHub's choices, which matter most to anyone tuning a MapHub of their own or choosing another model. These tests were made on the prototype's listings and participants, in astronomy and AI. They are early impressions from small samples (10 papers in the first test, one 171-paper day in the full-day check, five participants), not benchmarks. A new MapHub, or a new model, is best tested by hand first, the same way.

### Choosing the model

**First test (Oct 6, 2026).** One participant's portfolio (about 4,100 tokens; arXiv IDs and numbers take many tokens) against 5 astro-ph and 5 cs.AI papers: about 570 tokens per paper, 2–3 s per request, and about $0.05 on Opus 5.5. The same 10 papers on three models:

| Paper | Opus 5.5 | Sonnet 5.5 | Haiku 4.5 |
| --- | --- | --- | --- |
| Asymmetric beam treatment for CMB maps | 35 | 22 | 30 |
| Training numerical intelligence (LLMs) | 15 | 6 | 60 |
| Galaxy environments with manifold learning | 12 | 8 | 30 |
| Lensed clumps at z = 1–4 | 10 | 6 | 30 |
| The other six | 1–3 | 1–3 | 0 or 30 |

Sonnet 5.5 kept Opus's order at half the price. Haiku 4.5 mostly used the anchor values and put an LLM paper first, so it is ruled out.

**Full-day check (Oct 5–6, 2026).** All 171 papers of the Oct 5 listing, scored for all five participants on both models: Sonnet 5.5 ranked them much like Opus 5.5 (rank correlation 0.89–0.96 per column, 3–5 of each top five shared) but compressed the top of the scale (one column's best paper: Opus 45, Sonnet 22) and missed cross-topic matches that MapHub is meant to find (one paper: 62 against 22; another: 30 against 0). For a paper listed in a participant's own portfolio, Opus gave 95 and Sonnet 72 at low effort and 55 at medium; medium effort added no thinking, and the two Sonnet runs differed only by chance. Decision: Opus 5.5 at low effort. If cost ever forces a cheaper model, a prompt that pins papers listed in a portfolio near 100 is the first thing to try.

### Two passes and usage

**Two-pass test (Oct 14, 2026).** Most cells score low: on the Oct 14 listing, 97% of cells were below 30, and 90% of papers were below 30 for every participant. Scoring those precisely is wasted usage, so a cheap first pass picks out the papers worth a full read. Measured on the Oct 14 and Sep 8 listings (748 papers, five participants, scored with v0 the same day), with costs in API-equivalent dollars through Claude Code:

- **Each participant's outline in their own request** saves little. The papers are about 80% of a request (about 32,000 tokens per 50 papers, against 4,000–8,000 for a full portfolio), so such a first pass costs about 85% of a full run, and the whole two-pass run 89–108%.
- **All outlines in one request** (the joint outline) sends the papers once: the outline pass cost about $5.4 against about $24 for the v0 run. With a full pass for outline scores of 10 or more (13% of cells), the run comes to about 36% of v0, and it missed 2 of the 137 cells that v0 scored 30 or more (both scored 30, with outline score 5) and none of the 56 at 40 or more. A threshold of 5 missed nothing at about 46%; one of 15 missed 6 cells at about 31%. Outline scores come in steps of 5 and run about half as high as full scores, so they serve only as a filter.
- **The Overview matters.** Outlines made only of headings, bold phrases and Expertise lines missed 20 of one participant's 52 cells at 30 or more, papers on a field whose interest was written only in the Overview.
- **The outline's form matters little.** On a stratified subset of 150 papers, outlines of headings with each topic's opening sentence, its Expertise line, or both (with the Overview, about 1,700–2,900 words for five participants) missed 0–2 of 101 cells at 30 or more and cost 33–38% of v0, the same within noise. The format keeps the Expertise line, which portfolios already had, and adds a Next line so that plans show in the outline.
- **End to end** (50 papers from the subset, with the portfolios in the new format): the outline pass missed none of the 28 cells v0 scored 30 or more, and the full pass came within 10 points of v0 for 95% of the 58 cells it rescored (mean −2.5 points).
- **v0 and v1 on the same day** (Oct 15, 2026): a backfill of the Sep 1 listing begun with v0 and finished with v1 left both sets of scores for 94 papers (423 cells), with the same portfolios. v1 missed none of the 6 cells v0 scored 30 or more (all had outline scores of 10 or more); the 398 cells left with outline scores had v0 scores of at most 20 (one at 20); and the full pass came within 10 points of v0 on all 25 cells it rescored (72% within 5, mean +2.6). Near 30, scores moved both ways (9 cells at 30 or more with v1, 6 with v0). Since the two comparisons shift in opposite directions (−2.5 and +2.6), the full pass, which sees only the papers that passed the outline, scores like a v0 run within run-to-run noise.
- **Prompt or portfolios** (Oct 30, 2026): 198 papers drawn across the tables scored with v0 (Sep 1 – Oct 14), scored again with v2 and the current portfolios. Where the portfolios were already in their standard format (Sep 1–7, 28 papers), the same 6 cells scored 30 or more both ways, 5 within 10 points (rank correlation 0.78); where they were not (Sep 8 – Oct 14, 170 papers), cells at 30 or more went from 24 to 15 (rank correlation 0.48). The portfolios' change mattered far more than the prompt's, so the tables of Sep 8 – Oct 14 were rescored, all five columns (RUNNING.md, Stages: Second pass), and those of Sep 1–7 kept.

Decision: two passes with the joint outline and a threshold of 10 (prompt v1). The first v1 runs (Oct 15, 2026) came to 36–45% of v0's usage, with 4–15% of most columns' cells and 25–32% of one column's promoted to the full pass.

A check against blind ratings (Oct 19, 2026): the 23 rated cells that stopped at the outline pass though a rater gave them 30 or more, and two from an earlier round, were scored against the full portfolios, and none reached 30 (the highest, 25, for a paper rated 70), so the threshold lost nothing the full pass would have kept.

**Caching test (Oct 19, 2026).** Through Claude Code, each request wrote its whole prompt to the cache (25–39k tokens) but read back only about 600 tokens (Claude Code's own prefix), since the cache is matched up to the end of the message and the papers differ from request to request. Three outline requests of the Oct 16 listing were sent two ways: with the joint outline before the papers in the message, nothing more was read; with the instructions and joint outline in the system prompt and only the papers in the message, the second and third requests read 9,050 tokens from the cache. Scores were unchanged within run-to-run scatter (outline scores differed by 0.8 points on average; 1 of 26 cells scored 30 or more fell below 10, 5 cells rose to 10 or more). Decision: prompt v2, with v1's wording in that order, from Oct 19, 2026 (configuration log); a full-pass request through it matched the table's scores. On the host computer's backfills (Oct 19–20), v2 came to $0.84–0.94 per 100 papers at API prices, about 30% less per paper than v1's $1.30 (Oct 15), and a 5-hour window of the seat scored about 2,700 papers, against about 1,900 with v1 (Oct 16); a window's limit was worth about $20–25 at API prices with either prompt.

**Budget (Oct 5–20, 2026).** Measured on Opus 5.5 at low effort for five participants with prompt v0: about $1.50 for the 171 papers of Oct 5 (about $1.60 with retries) and about $2.50 for the 345 of Oct 6, on the API with caching; Tuesday listings include the weekend and run larger. Each further participant adds about 30% of the first one's cost, since only the first writes the cached papers block (about $0.17 against $0.05 per chunk of about 43 papers); ten participants on a typical day of about 200 papers come to roughly $2.90 a day, or about $60 a month over 21 announcement days. Portfolios, re-sent with every chunk, are a large share; chunks of 100 papers would cut it if scoring holds up on longer lists. Sonnet 5.5 would cost about half ([Full-day check](#choosing-the-model)).

With two passes (prompt v1), the Oct 14 and Sep 8 listings came to about a third of v0's cost ([Two-pass test](#two-passes-and-usage)): the outline pass sends each chunk's papers once for all participants, so a further participant adds mainly their outline (about 700–1,000 tokens per request) and the full pass over roughly a tenth of the papers. API use is billed separately from Claude subscriptions; the prototype ran on the API until Oct 8, 2026 and on a Claude Code seat since ([RUNNING.md, Local runs](RUNNING.md#local-runs)), so these figures matter for anyone running a MapHub through the API.

For the legacy survey through a Claude Code seat: with prompt v0, on Oct 12, 2026, four and a half backfill days filled one 5-hour window of a seat; with v1, on Oct 16, about ten and a half; with v2, on Oct 19–20, 16–19 listings of April–May 2026 (about 2,700 papers) used up each window in about half an hour. Subscription limits change over time, so these figures are a guide only: before a long survey, measure your own seat's usage on a few listings.

### Stability and quality

**Run-to-run check (Oct 18, 2026).** 275 papers from the listings of Jun 30–Sep 1, Oct 15 and Oct 16 (scored with prompt v1 and the current portfolios), drawn mostly from near the top of each column, were scored again once, for all five participants, with the same model, effort, prompt and portfolios. Scores fell by 4 points on average, and the mean absolute change was 5 points (median 5; 87% within 10), partly regression toward the mean, since most papers had been selected near the top; each column kept its order (Spearman's rho 0.96–0.99). Papers that had scored 0–9 moved by under 1 point, and none crossed 30; about half of those that had scored 30–49 fell below 30. A score near 30 is therefore a soft line, while the order of a column is stable.

**Run-to-run check, across the range (Oct 19, 2026).** 55 papers drawn across the whole score range (astro-ph weighted toward high scores, and cs.AI), from the 70 listings scored with the current portfolios, were scored again once for all five participants with the same settings. The mean absolute change was 1.7 points, and 4 of the 275 cells (55 papers × 5 columns) crossed 30: away from a selected top, scores are stable.

**Rating study (Oct 19–20, 2026).** Participants rate one shared list blind, as arXiv lists the papers, for themselves or their group, on the rubric: 45 astro-ph papers drawn with probabilities rising with a paper's highest score (proportional to 2^(s/20)), 10 cs.AI papers drawn across one column's scores, and five repeats, leaving out the raters' own papers; each rating is weighted by the inverse of its paper's chance of being drawn, so the results estimate what reading the 70 listings scored with the current portfolios would find. Since raters read the rubric differently and only the order matters, a paper counts as of interest if it is in its rater's top 5% (or 15%) of those listings by their own ratings. With one rater so far (the maintainer, rating for every column), reading papers in MapHub's order found 83% of the rater's top 5% within the top tenth of a listing (68% interval 62–88%; the top 5% rests on few papers), against 35% for a word-matching baseline (TF-IDF of title and abstract against the portfolio) reading the same share; of the top 15%, MapHub's top tenth held 33% against 15%, and TF-IDF catches up once about a third of a listing is read. Fixed ratings (50 and 30) give the same picture. More raters would make it firmer; a research note is in preparation.

### The OAI-PMH cache

**OAI-PMH test (Oct 16, 2026).** A backfill run stopped when the arXiv API answered 429 (Too Many Requests) for over an hour, after eight listings; rebuilding a past listing took eight or more API requests, one per configured category. arXiv's OAI-PMH interface, its route for bulk metadata, answered meanwhile. Harvesting the `physics:astro-ph` and `cs:cs:AI` sets from Aug 17 to Oct 16 took 20 requests (6 and 14; 71 MB, about 2 minutes) and covered some 40 listings, with titles, authors and abstracts. Rebuilt from those records with the same windows and category rule, every backfilled table from Aug 20 to Oct 2 matched paper for paper; the only extras were six papers held for moderation, already in later October tables, which the rule against scoring a paper twice leaves out. Tables from Oct 5 on follow the RSS feed's announcement dates and differ by moderation and holiday shifts, as an API rebuild would. Decision: past listings come from an OAI-PMH cache, with the API as the fallback.

**OAI-PMH count check (Oct 19, 2026).** Counted by ID month (the month of announcement), the cache's records matched the totals on arXiv's monthly listing pages exactly: astro-ph 2,250 for July and 1,977 for August 2026, cs.AI 5,389 for August, cross-lists included in both. Papers held for moderation keep their earlier submission dates (544 of August's cs.AI IDs were submitted in April to July), so a month is compared once the cache reaches six months before it. For older years, 10 papers sampled from each of arXiv's astro-ph listings for March 1993, June 1998, June 2003 and June 2006 were all in OAI-PMH, with submission dates and categories. Decision: the backfill checks each month once, warns on a difference, and goes on.

## Extension directions

Where MapHub could go next:

- **Cross-lists.** Add papers from other categories that are cross-listed to the configured listings.
- **Replacements.** Add revised versions of earlier papers, perhaps only when the abstract has changed.
- **More text.** Score from more than the title and abstract, such as the introduction and conclusions.
- **Participants' own repos.** An advanced option for anyone who needs a private portfolio: a participant keeps their portfolio in their own repo, likely through a small GitHub App they install so the daily job can read it there.
- **Other providers.** The scorer calls only Claude (Claude Code or the API); another model provider would need its own request function (`--via`).
- **A check of portfolio changes.** A GitHub bot that checks pull requests to the portfolios (own folder only, length), instead of the maintainer's review alone.
- **Missing participants in the viewer.** Some participants have no column on a given day: they joined later, or chose status no-legacy. For them, the daily job would keep a long-term correlation table between participants, built from every day on which both have scores. A user could still select a missing participant: other participants would then be sorted by long-term correlation with them, and papers by a weighted sum of the present participants' scores, marked as an estimate. To start, each present participant's weight would be their long-term correlation with the missing one, positive correlations only; weights fitted by regression are a later option. The viewer would then read one day's table plus the correlation table.
- **Driver logs.** Once the legacy survey's first pass is done, the driver's logs can go back to one file a month (one a day while it runs, all kept).
- **Viewer.** Ranking top papers by a set of participants (their average score); column headers that stay in view while scrolling, LaTeX in titles shown as math (e.g. `$z=1-4$`), and a more compact row layout for large listings.

## Parameters to tune

The settings a MapHub may adjust, each with the prototype's value and the evidence behind it ([Measurements](#measurements)); the first four are entries of `config-log.json` or the portfolio format, so a change is dated and recorded.

- **Model and effort level:** Opus 5.5 at low effort. Sonnet 5.5 kept Opus's order at half the price but compressed the top of the scale and missed cross-topic matches (First test, Full-day check); a cheaper model is worth trying once the ratings can judge it.
- **Two-pass threshold:** an outline score of 10 sends a paper to the full pass (prompt v1 and later). It lost nothing against blind ratings (Two-pass test, with the check of Oct 19, 2026); more days and more participants, especially those whose cells are rarely promoted, would show whether it holds.
- **Papers per request:** 50. A hundred would cut the usage of both passes further (Budget), if scoring holds up on longer lists, which is not yet tested.
- **Portfolio length and outline:** about 1,500 words for a person and 3,000 for a group, with an outline (the Overview, and each topic's heading with its Next and Expertise lines) of about 500 and 700 words; the Overview matters, the outline's exact form little (Two-pass test).
- **Top-papers floor:** the viewer's yearly summaries keep scores of 30 or more ([RESULTS.md, Web viewer](RESULTS.md#web-viewer)), the rubric's "may broaden their view". It is set in `daily_table.py` (`TOP_FLOOR`), not in the configuration log; after a change, `daily_table.py --rebuild-top` rewrites the summaries.

How well the scores match participants' own judgments is the subject of the rating study ([Measurements, Rating study](#stability-and-quality)) and of a research note in preparation.

## Sources

- [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions): standard GitHub-hosted runners, which publish the viewer, are free for public repositories.
- [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows): schedules use UTC and may start late under load, which retired the scheduled scoring.
- [arXiv API terms of use](https://info.arxiv.org/help/api/tou.html): at most one request every 3 seconds, over a single connection.
- [arXiv OAI-PMH](https://info.arxiv.org/help/oa/index.html): bulk metadata by set (such as `physics:astro-ph`), selected by the date a record last changed, with the `arXivRaw` format giving each version's submission time.
- [arXiv availability](https://info.arxiv.org/help/availability.html): submissions received by 14:00 ET are announced at 20:00 ET the same day; Friday-to-Monday submissions are announced Monday evening.
- [arXiv RSS feeds](https://info.arxiv.org/help/rss.html): the current listing, with each paper's announce type (new, cross-list, replacement).
- [DataCite REST API](https://support.datacite.org/docs/api): metadata of registered DOIs, including arXiv's, readable from a browser.
- [arXiv on Wikipedia](https://en.wikipedia.org/wiki/ArXiv): arXiv began on August 14, 1991.
- [Claude Message Batches API](https://platform.claude.com/docs/en/build-with-claude/batch-processing): half-price requests, usually done within an hour (24 hours at most), and the discount stacks with prompt caching.
- [Claude prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching): cached input is read at a fraction of the base price; writing the cache costs 25% extra.
